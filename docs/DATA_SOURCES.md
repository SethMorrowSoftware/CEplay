# Data Sources — which pages and functions query a database vs. call an API

A map of every page, endpoint and library function in this app against the
three places data actually comes from. Written because "DB query vs API call"
is not a clean binary here: most of the SQLite tables are *derived* from one of
the other two sources, so a page can be reading a local database and still be
answering a question about the card system or the POS.

Generated by inspecting `api/`, `lib/`, `public/js/` and the CLI scripts.

---

## The three sources

| # | Source | Layer | Direction | Notes |
|---|--------|-------|-----------|-------|
| 1 | **SQLite** — `data/pause_groups.db` | `lib/db.php` (`DB::query/each/queryOne/execute/getConfig`) | read + write | The app's own database. 26 tables. Also the cache/rollup layer for sources 2 and 3. |
| 2 | **MSSQL** — CenterEdge POS database | `lib/mssql_client.php` (`MssqlClient::rows/scalar`) | **read-only** (single-SELECT guarded) | Every reporting page. Venue server only — the sandbox has no driver. |
| 3 | **CenterEdge REST API** | `lib/centeredge_client.php` (`$client->…`) | read + **the only write path** | Games, kiosks, cards, capabilities, play-transaction feeds. SHA-1 auth, bearer token cached in `api_config`. |

### The thing that makes this list non-obvious

SQLite plays three different roles, and they read identically in the code:

- **Own data** — `pause_groups`, `schedules`, `schedule_overrides`,
  `scheduled_actions`, `admin_users`, `roles`, `action_log`, `reader_groups`,
  `promo_batches`, `watch_items`, `api_config`. Nothing upstream. A DB query
  here is genuinely just a DB query.
- **Cache of the CE REST API** — `game_state_cache`, `kiosk_state_cache`,
  `game_play_transactions`, `system_transactions`, plus the
  `cache_categories` / `cache_capabilities` JSON blobs in `api_config`
  (6h TTL, `readJsonCache`/`writeJsonCache`). Filled by
  `syncGamesToCache()` / `syncKiosksToCache()` / `pollAllGameTransactionFeeds()`.
  A page reading these is reading the card system *on a delay*.
- **Rollup of MSSQL** — `venue_daily_stats`, `game_daily_stats`,
  `game_hourly_stats`, `card_activity`. Filled by the nightly backfills in
  `lib/scheduler.php`. The Analytics deep-history view is a SQLite read whose
  numbers originate in the POS database.

So: **`#/analytics` never opens an MSSQL connection, but its Year view is POS
data.** And **`#/games` never calls the API on a normal load, but it is showing
card-system state.**

Only two paths write anywhere: SQLite (everywhere) and the CE REST API
(pause/unpause/tag-out, kiosk actions, RPC actions). MSSQL is read-only by
construction.

### Both (SQLite read/write + a live upstream call in the same request)

| Endpoint | SQLite part | Upstream part |
|---|---|---|
| `GET /api/games` | `game_state_cache` list | CE API auto-sync **only when the cache is empty** |
| `GET /api/kiosks` | `kiosk_state_cache` list | same lazy-sync fallback |
| `PATCH /api/games` | writes cache + `action_log` | CE API `patchGames` |
| `POST /api/games/unpause-all` | group/member resolution, audit | CE API patch per group |
| `POST /api/groups/{id}/action` | override + audit rows | CE API patch via `Scheduler::executeStateChange` |
| `GET /api/items`, `/api/promotions` | definitions from `watch_items` / `promo_batches` | MSSQL for every number |
| `GET /api/explorer/history-sources` | game names from `game_state_cache` | MSSQL probes |
| `PUT /api/*/settings` (6 report pages) | saves SQL to `api_config` | MSSQL validation round-trip |

DB query.

### `lib/centeredge_client.php`

Every `get*` / `patch*` / `perform*` / `poll*` method is an HTTP call. The ones
that also touch SQLite are the ones that *persist* what they fetched:

- `loadConfig` `authenticate` — read/write credentials + cached token in `api_config`
- `readJsonCache` `writeJsonCache` `invalidateCategoriesCache` `invalidateCapabilitiesCache`
- `syncGamesToCache` `syncKiosksToCache` — API → `game_state_cache` / `kiosk_state_cache`
- `pollGameTransactions` `pollSystemTransactions` — API → `game_play_transactions` / `system_transactions`

### `lib/mssql_client.php`

`settings` and `connect` read the encrypted connection config out of SQLite
`api_config`; `scalar` `scalarText` `rows` `assertReadOnly` `bindDate`
`bindRange` `bindCardRange` `bindIntList` are the MSSQL layer proper.

`cron.php` is the only place all three meet in one process: it syncs games and
kiosks from the **CE API** (steps 1/1b), plans and purges in **SQLite**

`cron_watchdog.php` is deliberately **MSSQL-free** — it is the safety-critical
pause/unpause path and runs on the stock `php:fpm` image. That is why the daily
unit needs the pdo_dblib overlay and the watchdog does not.

The two Slack bots read **MSSQL only** for the roster (`dbo.Employees`); they
touch SQLite just to resolve their `*_config` settings and write audit rows.
Neither calls the CenterEdge REST API at all.

## Quick answers

- **"Which pages never touch a network service?"**
  Schedules, Overrides, Logs, Login, Reader Groups, Performance, Analytics.
  All SQLite, all fast, all work with the POS and card system unreachable.
- **"Which pages break when MSSQL is down?"**
  Labor, Card Loads, Ticket Trends, Revenue Mix, Redemption, Explorer,
  Birthdays, Anniversaries — and the *stats* half of Promotions and Item Watch
  (their definitions still list). Each reports `{error}` at HTTP 200 on the
  panel rather than a 500.
- **"Which pages break when the CenterEdge API is down?"**
  Cards (entirely). Kiosks loses every action and the detail view. Games and
  Tag Board still *render* from cache but cannot pause anything. Everything
  else is unaffected until the cache goes stale.
- **"Where does a pause actually happen?"**
  `Scheduler::executeStateChange()` → `CenterEdgeClient::patchGames()` /
  `patchKiosks()`. Reached from the watchdog, `run_action.php`, the group
  action endpoints, and the per-request Tier 2 safety net in `index.php`.
