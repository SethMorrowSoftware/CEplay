# Grafana Instability — Incident & Resolution Notes

**Date:** 2026-05-15 (symptoms over the preceding ~4 days)
**Host:** webserver (192.168.1.11) — Fedora CoreOS, Hyper-V VM (on-premises)
**Impact:** Grafana intermittently slow, then unreachable (HTTP 502/504). CEplay/pause-groups briefly affected during the worst of it.
**Downtime:** Intermittent over several days; one ~10-minute planned outage for the RAM upgrade.

---

## Plain-English summary

Grafana was flaky for several days — loading very slowly, then throwing "Bad Gateway" errors instead of coming up. Two separate problems were behind it. First, the server only had 4 GB of memory and no swap (overflow) space, and Grafana uses most of that on its own — so any time it needed a little more, the whole server stalled. Second, every time Grafana restarted it got a new internal address, and the web server (nginx) kept trying to reach it at the old one. We added swap, capped Grafana's memory so it can't starve the host, pinned Grafana to a fixed internal address so nginx can always find it, and upgraded the VM from 4 GB to 8 GB of RAM. All fixes were tested and confirmed to survive a reboot.

---

## What happened

Over roughly four days, Grafana dashboards became progressively slower to load (15+ seconds), then began returning `504 Gateway Timeout` and later `502 Bad Gateway`. CEplay/pause-groups was briefly affected during the worst memory pressure but recovered on its own; Grafana did not, and went down repeatedly.

---

## Root causes

Two independent problems compounded each other.

### 1. Memory exhaustion — no swap

The VM had **3.8 GiB usable RAM and zero swap**. Grafana alone consumed ~2.6 GB steady-state and peaked at **3.3 GB** (confirmed in its shutdown log: `3.3G memory peak`). With no swap there was no buffer — once free memory hit ~130 MiB, any allocation stalled while the kernel reclaimed cache. Grafana couldn't respond in time, so nginx returned 502/504. These were **stalls, not clean crashes** — `journalctl` showed no OOM kills and no systemd restarts of `grafana.service` in the days prior.

Contributing factor: Grafana runs five app plugins and rebuilds its search index roughly every 30 seconds — constant memory churn against a host with no headroom.

### 2. nginx cached a stale upstream IP

nginx reaches Grafana through an `upstream` block in `/var/persist/nginx.conf`:

```nginx
upstream grafana {
    server systemd-grafana:3000;
}
```

Open-source nginx resolves names in an `upstream` block **once at config load** and caches the IP for the life of the process — it never re-resolves. Grafana runs on the `systemd-web` Podman network and gets a **new IP on every restart**. So each time Grafana restarted, nginx kept proxying to the dead IP → `502 Bad Gateway` until nginx itself was restarted.

---

## Changes made on this server (in order)

### 1. Added swap

A 4 GB swap file on the large persistent disk (`/var/persist`, ~115 GB free):

```bash
sudo dd if=/dev/zero of=/var/persist/swapfile bs=1M count=4096
sudo chmod 600 /var/persist/swapfile
sudo mkswap /var/persist/swapfile
```

Persisted via a systemd swap unit at `/etc/systemd/system/var-persist-swapfile.swap`, enabled with `systemctl enable --now`.

### 2. Capped Grafana's memory

systemd drop-in via `systemctl edit grafana.service` (survives Quadlet regeneration). Set to `MemoryHigh=2.5G` / `MemoryMax=3G` while the host still had 4 GB, then raised after the RAM upgrade (change 4) to give Grafana real headroom on the larger host:

```ini
[Service]
MemoryHigh=4G
MemoryMax=5G
```

`MemoryHigh` throttles Grafana into swap under pressure; `MemoryMax` is a hard ceiling. Worst case, Grafana alone slows or restarts — the host, sshd, and CEplay stay responsive.

### 3. Pinned Grafana to a static IP

Edited `/etc/containers/systemd/grafana.container`, changing:

```
Network=web.network
```
to:
```
Network=web.network:ip=10.89.0.50
```

Grafana now keeps the same IP across every restart, so nginx's cached upstream resolution never goes stale. No `nginx.conf` change required.

### 4. Upgraded the VM from 4 GB to 8 GB RAM

The VM runs on an on-premises Hyper-V host with **static memory**. Gracefully shut the VM down, changed the Memory setting in Hyper-V Manager from `4096` MB to `8192` MB, started it back up. ~10 minutes downtime. FCOS uses the extra RAM with no guest-side configuration.

### 5. Restarted nginx

Restarted `nginx.service` once so it re-resolved `systemd-grafana` to the now-permanent IP `10.89.0.50`.

|---|---|---|
| RAM | ~7.7 GiB total | `free -h` |
| Swap | 4 GB active | `swapon --show` |

| Containers | 4 running (grafana, nginx, tailscale, pause-groups-fpm) | `sudo podman ps` |
| Grafana IP | `10.89.0.50`, stable across restarts | `sudo podman inspect systemd-grafana --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'` |
| Grafana health | `database: ok` | `sudo podman exec systemd-grafana wget -qO- http://localhost:3000/api/health` |

A durability test confirmed the fix: restarting Grafana on its own (nginx untouched) kept its IP at `10.89.0.50` and nginx still returned `200`. A subsequent full host reboot confirmed every change above persists automatically.

## Recovery procedure if this recurs

**Grafana slow / 502 / 504:**

1. `free -h` — check memory and swap. The host now has 8 GB RAM + 4 GB swap, so memory exhaustion should no longer occur; if swap is heavily and persistently used, the VM needs still more RAM.
2. `sudo podman ps` — confirm the Grafana container is up.
3. `sudo podman exec systemd-grafana wget -qO- http://localhost:3000/api/health` — confirms Grafana itself is healthy. This bypasses nginx; note Grafana is **not** reachable on the host's `localhost:3000` (it's on the `systemd-web` Podman network).
4. If Grafana is healthy but the site still 502s, nginx has a stale upstream — `sudo systemctl restart nginx.service`. With the static IP this should no longer happen, but it remains the quick fix.

**After any Grafana restart:** Grafana keeps IP `10.89.0.50`, so nginx does not need restarting. If the IP ever comes back different, check that `/etc/containers/systemd/grafana.container` still has `Network=web.network:ip=10.89.0.50`.

## Open follow-ups

- **Kiosk auth loop.** The `wristband-expiration-inflatapark` kiosk dashboard (logged in as `userId=6`) fails authentication every 10 seconds — `error="[session.token.rotate] token needs to be rotated"` → HTTP 401. It is constant wasted load and log noise. A kiosk display should use Grafana anonymous auth or a service-account token, not a regular user session. Not a cause of the outage, but worth fixing.
- **`crane` upstream.** The `claw.thecastlefuncenter.com` vhost uses an identical name-based `upstream` block. If its backing container is also on the `systemd-web` network, pin it to a static IP (e.g. `10.89.0.51`) the same way to pre-empt the same 502 failure mode.
